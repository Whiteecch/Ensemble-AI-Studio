# 人际关系与场景推进 · 设计文档

> 第五批需求。五件事：**流式开口**、**诊断收进日志**、**场景自己跳时间**、**进离场要讲原因**、**人际关系成为一等实体**。

本文是设计基准与实现依据。与《信息库系统_设计文档》同期实施，两者有明确接口（见 §6.5）。

## 一、目标与范围

| # | 需求 | 一句话 |
|---|---|---|
| 1 | **流式输出** | 角色的台词逐字出现，不是一次性蹦出来。给"思考"留出时间，不那么生硬。 |
| 2 | **诊断收进日志** | 只有点了「显示日志」，上方才出现场景诊断；否则不显示。 |
| 3 | **场景跳时间** | 全员发言倾向都很低、且在进行持续性活动（睡觉/写作业）时，场景可自行推进时间并宣布活动完成。**严格限制，不许轻易跳。** |
| 4 | **进离场讲原因** | 高级移入移出界面可填加入/离开原因；进出前后，关系近的人之间会想告知或询问。 |
| 5 | **人际关系系统** | 每个有关系的人一行结构化信息（姓名/性别/亲密度/关系描述/相处模式）；描述与模式可被角色在思考阶段用工具**极少地**修改；亲密度参与计算；关系词条**恒在上下文**，而该角色的详细信息仍走信息库索引。 |

## 二、流式输出

### 2.1 现状

`graph.speak` 调 `ctx.speak.complete_text(msgs)`，拿到**整段**文本后才落一条 `block_spoken` 事件。用户看到的是台词"蹦"出来。

### 2.2 设计

- **后端**：新增流式调用能力（`DeepSeekBackend` 走 `stream: true` 的 SSE；`StubBackend` 给一个**确定性**的分片实现，供离线测试与演示）。既有的 `complete_text` / `complete_json` 一字不动。
- **事件**：新增一个"正在说"的流式事件（逐块增量）+ 收尾时照旧一条 `block_spoken`（**落点不变**，界面/引擎/存档都仍以它为真相）。流式只是**呈现通道**，不是新的真相源。
- **界面**：worker 把增量转成 Qt 信号（跨线程），主窗口把它追加进"当前气泡"；`block_spoken` 到达时就地把它**定稿**。

### 2.3 与复读抑制的冲突（必须处理）

现有语义：台词若与自己的近重复（`_is_near_repeat_of_own`）则**整块作废**、当作静默块。流式会让这段文本**先出现在屏幕上**再被判掉。

**决定**：流式文本先落进一个**临时气泡**（视觉上明确是"正在说"），收尾判定：

- 判定通过 → 就地定稿为正式行；
- 判定为复读 → **撤掉临时气泡**并照旧返回静默块。

复读是罕见路径，偶发一次"话说一半消失了"比"每次都等整段生成完才显示"划算得多。

### 2.4 节奏：接收侧全量缓冲，显示侧匀速吐字（实测后改定）

第一版把**显示节奏绑在了网络分片**上——每收到一片就整屏重绘一次。而 SSE 的分片是突发到达的（一次 recv 可能带来好几个 chunk，中间又静默一段），于是观感是**一顿一顿**的：忽快忽慢、还卡。

**决定：把两侧彻底解耦。**

| 侧 | 做什么 |
|---|---|
| **接收** | `_on_speak_delta` **只把片追加进缓冲，绝不触碰界面**（不重绘）——网络怎么抖都不影响观感 |
| **开吐** | `sig_speak_end(settled=True)` 到达（= 这一段的输出**已经全量收完**）才启动吐字定时器 |
| **吐字** | 一个 `QTimer` 按固定节奏推进"已显示"计数，每跳重绘一次；长台词有**加速上限**（整句 ~2.5 秒内吐完），否则一句长台词要吐十几秒 |
| **收尾** | 正式消息到达时**先扣住**（否则屏上会同时出现"吐到一半的气泡"和"完整的正式行"），吐完那一刻无缝换成正式行——文本同源，观感就是"这句话打完了" |

**"扣住"是渲染语义，不是留存的语义**：扣住的那条**当刻就按最终位置进留存**（`_hold_message` 把它插在气泡此刻所在的位置上），渲染时跳过它、改画吐字气泡。若等到吐完才入留存，就只能追加到末尾，而吐字窗口（最长 2.5 秒）里但凡又上屏一行——用户插话、场景叙述、导演行——那条**先发生的**台词就被永久排到它后面：对白区次序与引擎 id 次序相反、时间戳倒流，且 `_drop_from` 的位置截断会据此把引擎仍保留的那句台词一并吃掉。留存是 `_last_msg_id`、撤销/改写、换场清空共同的真源，行序必须"到达即定"。

代价照旧：模型说完了才开始显示，所以**没有"边想边说"的中间态**。换来的是**节奏恒定、不卡**——用户要的是后者。

### 2.5 吐字中的气泡，与正式行**同形**

第一版把吐字中的那一条画成**灰色虚线 + 「正在说…」**。用户的反馈是明确的：**不要灰的，要和正常一个形态**。

做法不是"把样式调一调"，而是**让吐字渲染复用正式行的渲染函数**（构造一份伪消息传进去）——"同形"因此是**结构保证**的，不靠人工对齐；将来改正式气泡的样式，吐字气泡自动跟着变。

### 2.6 不做什么

- 不改 JSON 类调用（think）的流式——它没有可读的中间态。

## 三、诊断收进日志

场景诊断（`sig_scene_diag`）现在常驻在上方。改成：**只有日志面板开着时才显示**。

- 日志面板的开合是既有的界面状态；诊断区跟随它显隐即可。
- 关闭时不占位、不闪烁（别用"隐藏但保留高度"那种把布局顶来顶去的做法）。

## 四、场景跳时间

### 4.1 什么时候可以跳

**两个条件同时成立**才允许：

1. **全员无话可说**：在场所有人的发言倾向（bid）**全部低于阈值**（0.5），且**连续 K 块**如此（K 由活跃度缩放，默认 3 块）；
2. **有一段持续活动**：场景里正在发生一件"要花时间的事"——睡觉、写作业、赶路、等天亮。

条件 1 是**引擎侧确定性判据**（复用 `dynamics` 已有的 bid，不新增数值系统）；条件 2 由场景 agent 判定。

### 4.2 严格限制（这是本节的重点）

跳时间是最容易被滥用的能力——一旦松，"戏"就变成了流水账。故设四道闸：

| 闸 | 规则 |
|---|---|
| **前件闸** | 条件 1 不成立**绝不跳**（引擎侧硬判，模型说跳也不跳——与 hook 的时间闸门同一套思路：模型判断 + 引擎否决）。 |
| **幅度闸** | 单次跳跃有上限（默认 8 小时），且**必须是钟点词能表达的整数**（30 分钟 / 1 小时 / 数小时 / 到次日清晨）。小幅度优先：能跳 30 分钟就不跳 3 小时。 |
| **冷却闸** | 跳过一次之后，**冷却 M 块**（默认 10）内不许再跳。 |
| **频次闸** | 整场戏的跳跃次数有上限（默认 3 次）。 |

### 4.3 落地产物

一条**叙述行**（与既有叙述同一条路），携带：

- 正文：`30 分钟之后……` / `到了第二天早上`；
- 一个**钟偏移量**字段（`clock_jump_minutes`）；
- **活动完成**的宣告（`作业终于写完了`）——这是这条行存在的意义：把"跳过的那段时间里发生了什么"一句话交代掉。

**虚拟钟**由 worker 持有（真实流逝 × 流速）。worker 派发这条行时把钟**前推**。图与引擎仍不持钟（既有分工不变）。

### 4.4 跳完之后

- 场景进入"活动已完成"的新状态，`plot_direction` 不变；
- 相关角色若在睡觉，其"唤醒"由**后续的进离场机制或场景叙述**负责，本期不做自动唤醒；
- 跳时间**不重置**沉默压力——跳过 8 小时不等于"刚说过话"。

## 五、进离场讲原因

### 5.1 输入

「高级移入移出」的界面（`hooks` 的延时角色动作 / `schedule_cast_change`）新增一个**原因**文本框。原因随动作一起入队、一起执行。

### 5.2 原因的去向

- 进离场的**播报行**照旧（`（X 走了。）`），原因**不**自动进这条公共行——不是所有离开都该被所有人知道；
- 原因进入**当事人自己的上下文**：他为什么走、他愿不愿意说；
- 引擎按**倾向**决定要不要落一条"说明行"或"询问行"：
  - 倾向 = f(话痨程度 `w5_talkativeness`, 两人间**亲密度**, 是否点名)；
  - 关系近、话多的人更会想说；关系近的人也会想问。
- 这条倾向**并入既有 bid 系统**（作为一项加权），不另开一套——与 `adjacency`/`silence_gain` 同一张表。

### 5.3 边界

- 没有原因（留空）时行为与今天**完全一致**（这一条要能测）；
- 离场者已经走了，他"想说"只能在**走之前**的一两块里发生（引擎侧有时序约束）；
- 不去替角色组织语言——**说什么由模型决定**，引擎只负责"这件事在他心里有分量"。

## 六、人际关系系统

### 6.1 一条关系长什么样

每个有关系的人**一行**：

| 字段 | 说明 |
|---|---|
| `name` | 对方姓名（键） |
| `gender` | 性别（自由文本，可空） |
| `closeness` | **亲密度 −100 ~ 100**（可负：仇视） |
| `description` | 关系描述（"同门师兄""有救命之恩"） |
| `mode` | 相处模式（"见面就掐，但出事一定护着"） |
| `updated_at` / `origin` | 何时、因何而变 |

### 6.2 它在哪里，和别的模块什么关系

**关键决定：关系是一条独立于信息库的"恒在上下文"的表，但它同时是信息库里的一类条目。**

- 关系**全部**恒在上下文（不像信息库索引那样按需取用）——因为"我对面这个人是谁"是**每一次开口都要用的**，不能等到想起来才用；
- 但对方的**详细信息**（一起经历过什么、他的底细、他的习惯）仍存在**信息库**里，靠键互相链接：关系行里带上该人物在信息库里的键，角色可以顺着读下去；
- 于是："关系表 = 永远在眼前的几行" + "信息库 = 想知道更多时去翻的书"。

物理落点沿用信息库那一套（`runs/<场景>/<角色名>/` 的副本、散场结算、本体库），关系表作为库里的一个**特殊分区**，不另造一套存储与结算。

### 6.3 谁能改：角色自己，但极少

角色在 think 阶段拿一个新工具改关系（`update_relation(name, description?, mode?, closeness_delta?)`）。

**触发频率必须极低**——这是本节最容易被做坏的地方。三重约束：

1. **工具描述写死**："只有在发生了**改变关系本质**的大事时才用（表白、决裂、救命、背叛）。日常寒暄、心情起伏、一次不愉快的对话——**都不算**。"；
2. **引擎侧频率闸门**：同一对关系**每场最多改 N 次**（默认 1 次），超出即拒绝并给模型一句说明；
3. **`closeness_delta` 有单次幅度上限**（默认 ±20），防止一次跳满。

> 与信息库工具同一套执行器、同一套"失败回文本不炸块"的契约。

### 6.4 亲密度参与计算

`closeness` 是**数值**，进 `dynamics` 的竞价（与既有 w 权重同源）：

| 项 | 效果 |
|---|---|
| `adjacency`（w3） | 说话人若是我关系近的人 → 更想接话 |
| `address_boost` | 被关系近的人点名 → 更想回应 |
| **进离场通知** | **A 对 B 的亲密度高于阈值时，B 进场会通知 A**（"他来了"这件事在我心里有分量）；低于负阈值同理（我心里一沉） |
| 沉默压力 | 关系近的人在场时，冷场更难熬（可后续调） |

### 6.5 与信息库的接口

| 事 | 谁做 |
|---|---|
| 关系表的读写、恒在上下文的渲染 | 本模块（新） |
| 关系行的**持久化与结算** | 复用信息库那一套（副本、pending、散场保留/丢弃） |
| 关系行里指向对方的**信息库键** | 渲染时附上，角色可顺链读 |
| 新工具 `update_relation` | 挂在既有工具层上（与 `read_entry`/`remember`/`revise` 并列），共用执行器与预算 |

## 七、分期与验收

> **实施状态：四期全部完成。** 本文保留为设计基准（记录"为什么这样做"），实际行为以代码与测试为准。
> 实现过程中经四轮对抗性评审，累计修掉数十处缺陷，其中若干条**只在实际跑起来才显形**——下面各期末尾的"实施记录"记的就是这些。

- [ ] 后端流式能力（deepseek 真流 + stub 确定性分片）
